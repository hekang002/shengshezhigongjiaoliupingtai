# 内容审核自动成单与事项分办设计

## 目标

将信息内容审核和事项分办拆成两个连续但职责独立的环节：内容审核决定是否发布，事项分办决定由谁办理。建言献策和心声诉求审核通过后自动生成可追溯的待分办事项，业务交流审核通过后直接发布。

## 业务边界

- 内容审核：审核通过或驳回，记录审核意见和发布可见性。
- 事项分办：设置主办部门、当前办理人、协同部门、优先级、办理期限、办理要求和答复方式。
- 承办人：分办后直接进入办理中，不设确认或接收环节。
- 转办：承办人提交转办申请，分办管理员处理后直接改派，新承办人不需再次接收。
- 答复审核：驳回时回到承办人修改，通过后按公开或私密方式反馈并办结。

## 状态模型

帖子保留三类独立状态：

- `contentAuditStatus`：待审核、审核通过、已驳回。
- `publishStatus`：未发布、已发布、私密发布。
- `handlingStatus`：不适用、待分办、办理中、待答复审核、退回修改、已办结。

兼容现有原型的 `status` 字段，但新的内容审核、分办和答复流转以三类独立状态为准。

## 页面结构

```
事项分办
├── 数据概览：待分办 / 办理中 / 待答复审核 / 临期 / 退回修改
├── 待分办
│   └── 查看来源内容并设置责任信息
├── 已分办
│   └── 查看办理轨迹、剩余时限、当前办理人和改派情况
└── 答复审核
    └── 审核正式答复并办结
```

## 关键交互

- 内容审核通过后显示新生成的事项编号。
- 待分办事项已经是事项记录，不再从帖子列表临时推导。
- 分办表单左侧显示来源内容和审核结果，右侧填写分办信息。
- 确认分办后事项立即进入办理中，并向承办人生成待办通知。
- 所有审核、分办、改派、答复审核和办结操作写入流转记录。

## 验收标准

- 审核通过一条建言献策或心声诉求后，事项分办的待分办数量增加，且可看到新事项编号。
- 审核通过业务交流后不生成办理事项。
- 分办表单必填校验有效，承办人必须属于主办部门。
- 分办完成后事项状态直接为办理中，不出现待确认或待接收。
- 原有本地演示数据加载后自动补齐新字段，不导致页面空白。
